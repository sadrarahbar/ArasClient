# راهنمای پیاده‌سازی برای ایجنت‌ها و برنامه‌نویس‌ها

[فهرست](README.md) · [معماری](ARCHITECTURE.md) · [آزمون و انتشار](TESTING-RELEASE.md)

## ۱. پیش از ویرایش، مقصد را مشخص کنید

```bash
git branch --show-current
git status --short
git branch -vv
```

| نوع کار | برنچ و مسیر مقصد |
|---|---|
| تغییر محصول اصلی Android و مدیریت چندپروفایل | `main` → `app/` |
| تغییر رابط Tesla Android یا سیاست تک‌کانفیگ | `Android-Client` → `app/` |
| تغییر Qt، routing و بستهٔ Linux | `Linux-Client` → `linux/` |
| تغییر WinINET، Wintun، UAC یا بستهٔ Windows | `Windows-Client` → `windows/` |
| مستندات مرکزی هر چهار محصول | `main` → `docs/fa/` |

وجود فایل در Explorer/IDE را با trackedبودن در گیت یکی ندانید:

```bash
git ls-files linux windows artifacts
git check-ignore -v path/to/file
```

در snapshot فعلی `main`، قواعد ignore خروجی‌های دسکتاپ از شاخه‌های محصول
به‌طور خودکار منتقل نشده‌اند؛ پوشه‌های محلی `artifacts/` و باقی‌مانده‌های
`windows/` می‌توانند untracked دیده شوند. آن‌ها را همراه مستندات stage نکنید.

دادهٔ staged/unstaged و فایل محلی کاربر را حفظ کنید. برای رفع اختلاف وضعیت،
`reset --hard`، `clean -fdx` یا حذف پوشهٔ ignored را به‌صورت خودکار راه‌حل ندانید.
نادیده‌گرفتن فایل در `.gitignore` آن را از کامیت‌های قبلی خارج نمی‌کند؛ این
موضوع به‌ویژه برای APK/EXE بزرگ و هویت WARP مهم است.

## ۲. ورودی و خروجی کار را بنویسید

پیش از تغییر، مشخص کنید مشکل در UI، parser، مدل، config builder، هسته، سرویس
یا OS integration است. برای نمونه:

- «دکمه بزرگ‌تر شود» → رابط و هندسه؛ نیازی به تغییر route یا identity ندارد.
- «لینک وارد نمی‌شود» → تشخیص قالب و parser؛ قبل از پاک‌کردن پروفایل قدیمی بررسی شود.
- «متصل نشان می‌دهد، اینترنت ندارد» → handshake، HTTPS، route، DNS و خروجی واقعی؛ صرفاً تغییر status راه‌حل نیست.
- «بسته روی دستگاه نصب نمی‌شود» → SDK، ABI، امضا، versionCode و فایل کامل بسته.

معیار پذیرش قابل مشاهده تعریف کنید: حفظ کانفیگ قبلی در ورودی نامعتبر، بازیابی
دقیق پراکسی بعد از قطع، یا نبود child و route باقی‌مانده بعد از crash.

## ۳. الگوی تغییر در Android

1. نوع ورودی و مدل را در `EConfigType`، `dto/` و `fmt/` ردیابی کنید.
2. برای UI، اکشن را از مسیر `MainAction` و ViewModel عبور دهید؛ Composable محل مدیریت process نیست.
3. ذخیره‌سازی را از `MmkvManager` / `AngConfigManager` انجام دهید؛ index و selection را جداگانه و بدون قرارداد publish تغییر ندهید.
4. تغییر config در builder مربوط باشد؛ تفاوت `CoreConfigContextBuilder`، outbound و transport حفظ شود.
5. helper را پیش از مصرف SOCKS آن آماده کنید و خطای آن را به lifecycle سشن برگردانید.
6. مجوز `VpnService.prepare`، foreground service و توقف وسط start را دور نزنید.
7. FD مربوط به TUN فقط یک خواننده داشته باشد؛ HEV و مسیر native موازی روی همان FD فعال نشوند.
8. در Tesla، parser کامل می‌تواند در کد باقی بماند، حتی اگر صفحهٔ مربوط در UI پنهان است؛ حذف قابلیت با تغییر نمایش یکی نیست.

برای افزودن پروتکل، یک برش کامل از parser تا هسته و تست بسازید. فقط افزودن
فرم یا enum می‌تواند کانفیگ ظاهراً معتبر ولی غیرقابل اجرا تولید کند.

## ۴. الگوی تغییر در دسکتاپ

| فایل | تغییر مناسب |
|---|---|
| `profiles.py` | شناخت قالب، محدودیت اندازه، اعتبارسنجی و ذخیرهٔ تک‌پروفایل |
| `runtime.py` | انتخاب پورت، account، env و argv؛ نام executable متناسب OS |
| `engine.py` | state، cancellation، readiness، probe و پایان سشن |
| `tun.py` | قرارداد helper و route/DNS؛ فقط API همان سیستم‌عامل |
| `system_proxy.py` | snapshot، اعمال و restore با حفظ تغییر مستقل کاربر |
| `win32.py` | فقط Windows؛ UAC، ACL و Job Object |
| `ui.py` | نمایش، ورود، دسترس‌پذیری و اکشن کاربر |
| اسکریپت ساخت | منابع محلی، مجوزها، خروجی و کنترل integrity |

- فرمان از متن کانفیگ نسازید؛ `argv` لیستی و بدون shell باشد.
- allowlist گزینه‌های Aether و مسیر executableهای مجاز را تضعیف نکنید.
- `private_write` و اصل «ابتدا parse و ذخیره، سپس جایگزینی» حفظ شوند.
- فایل هویت renewشده را در هر reconnect با نسخهٔ قدیمی overwrite نکنید.
- listener داخلی WARP را با listener نهایی Psiphon عوض نکنید.
- بازبودن پورت، پذیرش SOCKS، موفقیت HTTPS و اعمال route را جدا بررسی کنید.
- schema sing-box لینوکس قدیمی و Windows 1.12 را با یک JSON واحد جایگزین نکنید، مگر با مهاجرت و آزمون هر دو.
- cleanup روی stop، timeout، child failure و EOF والد پوشش داده شود.

## ۵. قرارداد تغییر طراحی

دارایی‌ها و فونت باید داخل پروژه باشند؛ runtime به URL موقت Figma وابسته نباشد.
لوگو را با شکل تقریبی جایگزین نکنید. تغییر اندازهٔ دکمه، موقعیت لوگو، حاشیهٔ
داخلی و موقعیت status/test را نیز در بر می‌گیرد.

رنگ هاله و دکمه از یک وضعیت واحد مشتق شوند. در Android، مبنا ۴۵۱×۸۵۲ با دکمهٔ
۲۳۱ و مقیاس یکنواخت است؛ در دسکتاپ snapshot فعلی دکمه ۱۷۱ است. این دو طراحی
را ناخواسته روی هم کپی نکنید. تفاوت رندر Qt و AndroidSVG می‌تواند گرادینت را
عوض کند؛ تصویر runtime با فریم مرجع مقایسه شود.

در تست UI، فقط گرفتن screenshot کافی نیست: بریدگی متن، hit target، focus،
غیرفعال‌بودن Replace حین اتصال، QR بدون دوربین و RTL/LTR هم بررسی شوند.

## ۶. دادهٔ حساس و وابستگی‌ها

- نمونه‌ها فقط دادهٔ ساختگی داشته باشند؛ کلید کاربر، PEM، TOML واقعی، URL خصوصی اشتراک و لینک کامل export در کد/تست/مستندات قرار نگیرند.
- `session.json`، accountها و `proxy-recovery.json` نباید همراه installer بسته‌بندی شوند.
- permission/ACL حفظ شود؛ خطای chmod در Windows را معادل اعمال ACL ندانید.
- native dependency از انتشار رسمی با checksum ثابت بیاید؛ رفع mismatch با حذف کنترل hash پذیرفتنی نیست.
- برای تغییر هسته، نسخه، checksum، schema، فایل license و آزمون اجرایی هم‌زمان بررسی شوند.
- کتابخانه‌های آمادهٔ `app/libs/` با خروجی‌های تولیدی `artifacts/` یکی نیستند؛ فایل لازم برای build را کورکورانه حذف نکنید.
- الگوریتم رمزنگاری `.arasc` را از نام کتابخانه یا ظاهر UI حدس نزنید؛ تغییر آن نیازمند قرارداد و سورس/آزمون سازگار است.

## ۷. انتخاب آزمون

برای تغییر رفتاری، ابتدا regression مربوط و سپس مجموعهٔ مناسب همان محصول
اجرا شود. تغییر صرف متن یا فاصلهٔ UI به تستی که همان پیاده‌سازی را تکرار کند
نیاز ندارد؛ مشاهدهٔ خروجی و بررسی هندسه معمولاً مفیدتر است.

نتیجه باید محیط، فرمان، count/skip و محدودهٔ اثبات را داشته باشد. یک تست mock
نمی‌تواند اثبات کند route واقعی Windows درست است؛ تست Wintun بدون auto_route
هم اتصال خارجی VPN را ثابت نمی‌کند. دستورها در [آزمون و انتشار](TESTING-RELEASE.md) آمده‌اند.

## ۸. گیت، انتقال بین برنچ و تحویل

تغییرات مرتبط را با مسیر مشخص stage کنید؛ در محیطی که پوشه‌های خروجی مشترک
باقی مانده‌اند، از افزودن بی‌بررسی همهٔ فایل‌ها خودداری کنید:

```bash
git diff --stat
git diff --check
git add -- path/to/changed/source
git diff --cached --stat
```

در انتقال یک fix میان برنچ‌ها، تفاوت نسخهٔ هسته و API سیستم‌عامل را بررسی
کنید؛ parser می‌تواند قرارداد مشترک داشته باشد، ولی helper شبکهٔ لینوکس
نباید به ویندوز کپی و اجرا شود. commit کوچک و توضیح مسئله/رفتار/آزمون، review
را قابل انجام می‌کند. امضای انتشار و خروجی بزرگ در git commit قرار نگیرند.

Push، انتشار Release، force-push یا نصب روی دستگاه را با محدودهٔ درخواست کاربر
هماهنگ کنید. در کار مستندسازی حاضر، **Push با مالک پروژه است**.

### نگهداری مستندات در main

اگر روی محصول دیگری کار می‌کنید، برای اسناد مرکزی از checkout/worktree مربوط
به `main` استفاده کنید؛ ابتدا مطمئن شوید برنچ در مسیر دیگری checkout نشده و
تغییرات ذخیره‌نشده در معرض جابه‌جایی نیستند. به‌روزرسانی اسناد شامل این‌هاست:

- commit مرجع در [فهرست](README.md)؛
- OS/ABI و نسخهٔ هسته در صورت تغییر؛
- جدول پروتکل‌ها در صورت تکمیل واقعی زنجیرهٔ اجرا؛
- دستور build/test و شواهد آزمون؛
- بستن یا تغییر اولویت آیتم نقشهٔ راه.
