# Tesla Vpn برای ویندوز

این برنچ نسخهٔ دسکتاپ ویندوز است و از نسخهٔ Linux-Client مشتق شده است.

## سیستم موردنیاز

- Windows 10 نسخهٔ 1809 (build 17763) یا جدیدتر، و Windows 11؛ فقط x64.
- ویندوز ۳۲ بیتی و ARM64 بومی فعلاً هدف این بسته نیستند.
- بستهٔ نهایی به نصب Python یا Qt نیاز ندارد.

## اجرا

فایل `TeslaVpn-1.0.2-Windows-x64-Setup.exe` نصب‌کنندهٔ کاربری است؛ نصب اولیه
مجوز مدیر نمی‌خواهد. بستهٔ ZIP هم قابل‌حمل است: تمام پوشه را استخراج کنید و
`TeslaVpn.exe` را اجرا کنید. فایل EXE را از کنار پوشهٔ `_internal` جدا نکنید.

ظاهر، هالهٔ هم‌رنگ اتصال، تک‌کانفیگ و واردکردن از کلیپ‌بورد، فایل و تصویر QR
از نسخهٔ لینوکس حفظ شده است. تصویر QR بدون دوربین قابل ورود است؛ ضبط دوربین
در این نسخه ارائه نمی‌شود. واردکردن کانفیگ اشتباه، کانفیگ قبلی را حذف نمی‌کند.

- **System VPN · TUN** پیش‌فرض است. هنگام اتصال، UAC برای بازشدن برنامه با
  دسترسی مدیر نمایش داده می‌شود. اگر رد شود، برنامه باز می‌ماند و اتصال شروع
  نمی‌شود. از کل حساب جاری و شبکه‌های خودتان استفاده کنید.
- **System proxy** بدون دسترسی مدیر کار می‌کند. برنامه‌های مقصد باید از
  تنظیمات پراکسی ویندوز پیروی کنند؛ برنامه‌هایی با پراکسی اختصاصی یا سرویس‌های
  WinHTTP الزاماً از پراکسی کاربری WinINET استفاده نمی‌کنند.
- Wintun فقط در حالت TUN استفاده می‌شود. برای جلوگیری از حلقه، فقط مسیر دقیق
  هسته‌های بسته از TUN مستثنا شده است؛ برنامه‌های دیگر و مرورگرها مستثنا نیستند.
- DNS حالت TUN از HTTPS درون پراکسی عبور می‌کند. قبل از سبزشدن وضعیت، SOCKS
  و سپس مسیر مستقیم سیستم با HTTPS بررسی می‌شوند. برابری کشور خروجی نیز در
  صورت دریافت هر دو پاسخ کنترل می‌شود.

فقط یک VPN سیستمی را هم‌زمان فعال کنید. برای خروج، پنجره را ببندید تا تنظیمات
قبلی پراکسی بازگردد و پردازش‌ها متوقف شوند. Job Object ویندوز جلوی باقی‌ماندن
هسته‌ها پس از مرگ سرپرست را می‌گیرد. در حالت Proxy، مرگ رابط نیز از طریق EOF
به سرپرست اطلاع داده می‌شود تا تنظیمات بازیابی شوند. اگر بازیابی شکست بخورد،
نسخهٔ پشتیبان تا اجرای بعدی نگهداری می‌شود؛ تغییر مستقل کاربر بازنویسی نمی‌شود.

کانفیگ، هویت WARP و نسخهٔ پشتیبان پراکسی در `%LOCALAPPDATA%\TeslaVpn` با ACL
کاربر فعلی، SYSTEM و Administrators نگهداری می‌شوند و وارد بستهٔ اجرایی نمی‌شوند.
بسته و نصب‌کننده فعلاً امضای تجاری ندارند؛ Publisher مورداعتماد یا حذف هشدار
SmartScreen ادعا نمی‌شود.

## کانفیگ‌ها

همان ورودی‌های نسخهٔ لینوکس: خروجی Aether/Nekoray از اندروید، لینک‌های Aether،
VLESS، VMess، Trojan، Shadowsocks و SOCKS، JSON سازگار با Xray و فایل WireGuard.
این کار تبدیل MASQUE یا سایفون به پروتکل VLESS نیست. خروجی Aether دارای هویت
خصوصی است؛ آن را در گیت، گزارش ساخت یا منابع عمومی قرار ندهید.

## ساخت از سورس در ویندوز

Python 3.12 x64 نصب کنید و در PowerShell از ریشهٔ پروژه اجرا کنید:

```powershell
powershell -ExecutionPolicy Bypass -File windows/setup.ps1
powershell -ExecutionPolicy Bypass -File windows/build.ps1
```

برای اجرای سورس: `windows/run.ps1`.
آزمون‌ها: `windows/.venv/Scripts/python.exe -m unittest discover -s windows/tests -v`.
نصب‌کننده با Inno Setup 6 و `windows/installer.iss` ساخته می‌شود.
خروجی‌ها در `artifacts/windows/` هستند و در گیت ثبت نمی‌شوند.

هسته‌ها نسخه و SHA256 ثابت دارند و فقط از انتشار رسمی Aether، Xray، sing-box و
Wintun دریافت می‌شوند. فایل عمومی bootstrap سایفون از asset ثبت‌شدهٔ پروژه
استخراج می‌شود. مجوز هسته‌ها در `licenses/` همراه بسته است.

## ساخت بدون داشتن ویندوز

گردش‌کار `.github/workflows/windows.yml` روی `windows-2022` و Python 3.12 x64 اجرا
می‌شود؛ خروجی ZIP، Setup، checksum و تصویر پیش‌نمایش را به‌صورت Artifact می‌دهد.
سورس و ابزارها ارسال می‌شوند؛ EXE، DLL دانلودی و نصب‌کننده به گیت اضافه نمی‌شوند.
آزمون Wintun در CI عمداً مسیر پیش‌فرض سیستم را تغییر نمی‌دهد و کانفیگ واقعی
کاربر نمی‌خواهد. این آزمون جای آزمایش اتصال واقعی با یک کانفیگ معتبر روی
Windows 10/11 را نمی‌گیرد. Windows Server 2022 محیط ساخت است، نه مدرک آزمون
تمام نسخه‌های مصرف‌کنندهٔ ویندوز.


## اصلاحات نسخهٔ ۱.۰.۱

- EXE از نوع GUI/Windowed است و برای برنامه یا helperها کنسول ایجاد نمی‌کند.
  ارتباط stdin/stdout پردازش‌های داخلی از pipeهای به‌ارث‌رسیده بازسازی می‌شود.
- چرخش دکمه با QVariantAnimation پیوسته است و با به‌روزرسانی وضعیت دوباره شروع نمی‌شود.
- handshake سوکس و آماده‌شدن HTTP bridge رویدادمحورند؛ API پراکسی و نوشتن فایل
  روی worker سری اجرا می‌شوند تا UI هنگام اتصال و توقف مسدود نشود.
- لغو اتصال در زمان آماده‌سازی یا فعال‌کردن پراکسی، نتیجهٔ دیررس را نادیده
  می‌گیرد و بازیابی پس از عملیات فعال‌سازی انجام می‌شود.


## اصلاحات نسخهٔ ۱.۰.۲

توقف HTTP bridge با بستن کانال ورودی و EOF انجام می‌شود؛ helper بدون پنجره
پیام WM_CLOSE را دریافت نمی‌کند. تایمرهای kill نیز هر کدام process مربوط به
خود را capture می‌کنند تا باقی‌ماندن bridge پس از توقف core باعث گیرکردن
وضعیت Disconnecting نشود. تست دوحالت Proxy/TUN و lifecycle واقعی QProcess
با helper بسته‌بندی‌شده برای این مسیر اضافه شده است.
